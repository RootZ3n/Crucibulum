## 1. Doctrine doc path

`docs/CAPABILITY_CERTIFICATION_DOCTRINE.md` (new).

Defines:

- **5 tiers**: EXPERIMENTAL · PROVIDER_TESTED · STABLE · CAPABILITY_CERTIFIED · BLOCKED_UNSUPPORTED.
- For each tier, what it **may** and **may not** do (UI surface,
  model cards, leaderboard, release gate, general certification,
  capability-specific certification).
- **Vision promotion gates** (PROVIDER_TESTED, STABLE,
  CAPABILITY_CERTIFIED) with explicit numeric thresholds for suite
  size (5 → 15), repeat-run count (1 → 3), pass rate (80%),
  independent route families (1 → 3), and disallowed recurring
  attributions per tier.
- **Roleplay promotion gates** with explicit thresholds for suite
  size (7 → 20), repeat-run count (1 → 5), pass rate (80%),
  independent route families (1 → 3), NEEDS_REVIEW cap (<15%),
  zero recurring SEVERE persona-break / unsafe-compliance / HARD
  contradiction.
- **Evidence requirements** — every promotion above EXPERIMENTAL
  must cite verifiable artifacts (smoke reports, stability
  reports, audit cards, bundle ids, fixture sha256s, transcript
  excerpts, cost/tokens, attribution counts, commit hashes).
- **Schema / API design** for `core/capability-certification-types.ts`
  and `core/capability-certification.ts`.
- **UI requirements** — capability badges must never blend into the
  main leaderboard composite or `MODEL_CERTIFICATION.models[].tier`.
- **Non-goals** for this phase (no promotion, no UI badges, no
  HTTP endpoint, no `data/certified-capabilities.json` registry).

## 3. Schema / code added

### `core/capability-certification-types.ts` (new)

Type-only contracts:

- `CapabilityId` — discriminated union (`"vision" | "roleplay"`)
- `CapabilityTier` — closed 5-value union (`EXPERIMENTAL` |
  `PROVIDER_TESTED` | `STABLE` | `CAPABILITY_CERTIFIED` |
  `BLOCKED_UNSUPPORTED`)
- `CapabilityEvidenceRef` — `{kind, path, commit?, generatedAt?}`
  pointer to a verifiable artifact
- `CapabilityRouteCertification` — current tier for a route, with
  **literal-false** `affectsLeaderboard` + `affectsCertification`
  fields (compile-time enforced)
- `CapabilityGateFailure` — single blocking condition
- `CapabilityPromotionDecision` — read-only payload from the
  evaluator (`{eligible, blockingReasons, evidenceRefs, …}`),
  also with literal-false affects fields
- `CapabilityGateSpec` — threshold bundle per (capability × tier)

### `core/capability-certification.ts` (new)

Read-only evaluator:

- `VISION_GATES` and `ROLEPLAY_GATES` — per-tier
  `CapabilityGateSpec` maps with the numeric thresholds from the
  doctrine doc.
- `gateSpecFor(capability, tier)` — lookup.
- `evaluatePromotion(input)` → `CapabilityPromotionDecision`. Walks
  every gate clause for the proposed tier, collects all blocking
  conditions, returns the decision. Multiple blockers in one call
  so the operator sees the full gap.

Guarantees:
- Never mutates `MODEL_CERTIFICATION.models[]`.
- Never touches `certified-models.json`.
- Never affects leaderboard composite.
- BLOCKED_UNSUPPORTED routes cannot move to higher tiers without
  explicit re-test resolution.
- Promotion above EXPERIMENTAL with empty `evidenceRefs` is
  structurally impossible.

No HTTP endpoint, no UI badges, no `data/certified-capabilities.json`
in this phase (deferred per the roadmap to D / I / J).
