### Headline differences

- **v2.5 vs v2-omni:** matches v2-omni's post-Phase-12 stability
  (both 15/15), but **does not exhibit the verbose-chain-of-thought
  uncertainty quirk** that forced the Phase 12 scorer calibration.
  v2.5's uncertainty responses were short and direct, so the
  scorer's semantic check did not need the verbose-but-safe path
  to PASS them. Costs are **~9× lower** at the same stability
  level ($0.0004 vs $0.0036).
- **v2.5 vs gpt-5.4-mini:** strictly better on this 5-test profile.
  v2.5 passes `vision-object-count-001` (counts the 7 dots
  correctly), where gpt-5.4-mini consistently miscounts as 6.
- **v2-omni remains the legacy/proven fallback.** Phase 13-A does
  not deprecate or remove it; the registry entry is unchanged. A
  future explicit migration phase can flip default selection to
  v2.5 if subsequent evidence holds.

## 14. Final recommendation

**Replace v2-omni with v2.5 as the future Vision default candidate;
keep v2-omni in the registry as the proven/legacy fallback until a
future explicit migration phase.** Phase 13-A evidence is
sufficient for a candidate verdict; full default-switch needs:

- ≥1 month of operator-use evidence on v2.5 (no provider regression).
- Roadmap Phase C suite expansion (5 → 15 Vision tests) re-run on
  v2.5 to confirm the 100% rate holds at the larger suite.
- Roadmap Phase E third-route validation, so v2.5 is not the only
  candidate when defaults switch.
- Roadmap Phase D promotion HTTP path so the change goes through
  the doctrine-aware promotion endpoint, not a manual config edit.

Until those phases land, v2.5 stays a **validated replacement +
validated daily-driver candidate** and v2-omni remains the
in-registry default. The UI block + this report + the docs
section are the surface where operators can find the candidate
state.
