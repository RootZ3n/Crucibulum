## 4. Recurring / intermittent / suspect findings

### SCORER_SUSPECT — `mimo-v2-omni` · `vision-uncertainty-001`

Three repeats, three failures, all attributed `SCORER` with reasons
`"answer too verbose: 853 chars (max_chars 600)"`, `"… 820 chars …"`,
`"… 998 chars …"`. The mimo model produces chain-of-thought style
800–1000 char responses that exceed the manifest's `max_chars=600`
cap. Per Phase B rules, **the scorer is not changed in this phase**:
the runner records this as repeat-run evidence that the
`uncertainty_honesty` `max_chars` ceiling is too tight for this
model's response style, and defers the fix to a future calibration
phase (see _Open follow-up_ below).

The classifier reached SCORER_SUSPECT via the "all failures share
SCORER attribution" branch added during Phase B (the earlier roleplay
implementation only fired SCORER_SUSPECT on same-reason recurrence,
which would have missed this case because each failure's char count
differs).

### RECURRING_FAIL (MODEL) — `gpt-5.4-mini` · `vision-object-count-001`

Three repeats, three failures, all attributed `MODEL`. The model
consistently counts 6 dots in the seven-dot fixture (`numeric_fact_match`
expects `"7"`). This is honest model failure — not a scorer or
fixture problem. No mitigation is required; the model genuinely
cannot do this counting task at this image resolution.

### No INTERMITTENT_FAIL, no NEEDS_REVIEW_STABLE, no CONFIG/PROVIDER/FIXTURE_SUSPECT

Across 30 (test × run) cells the only failure attributions seen were
`SCORER` (3 cells on mimo) and `MODEL` (3 cells on gpt-5.4-mini).
There were no intermittent failures and no NEEDS_REVIEW outcomes —
the smoke is reproducible.

## 6. Dry-run gate eligibility (read-only)

Both stability reports embed a `dryRunGateEligibility` block produced
by calling `evaluatePromotion()` against the Phase A doctrine. The
block is explicitly labelled
`"DRY-RUN ELIGIBILITY CHECK (read-only; no mutation performed)"`,
carries `affectsLeaderboard: false` and `affectsCertification: false`
on every nested decision, and never writes to
`MODEL_CERTIFICATION.models[]` or `certified-models.json`.

### `xiaomi/mimo-v2-omni`

| Proposed tier | Eligible | Notes |
|---|:--:|---|
| PROVIDER_TESTED | ✅ | meets evidence, suite size 5 ≥ 5, repeats 3 ≥ 1, routes 1 ≥ 1, no recurring CONFIG/PROVIDER |
| STABLE | ❌ | **blocked by `vision.stable.recurring-scorer`** — recurring SCORER attribution disallowed at STABLE tier |

### `gpt-5.4-mini`

| Proposed tier | Eligible | Notes |
|---|:--:|---|
| PROVIDER_TESTED | ✅ | same as above |
| STABLE | ✅ (dry-run) | 80% stable-pass rate meets gate; recurring MODEL not in disallowed list (MODEL = honest model failure) |

**Doctrine reading.** STABLE means *scoring is stable*, not *the model
never fails*. A route can be STABLE-eligible while still failing one
test if those failures are MODEL-attributed (honest miscounts, honest
miscalls). It cannot be STABLE-eligible while recurring SCORER
attributions exist, because that signals the *measurement* is what's
moving around. The Phase B baseline produces both flavours of
evidence — mimo demonstrates a recurring SCORER, gpt-5.4-mini
demonstrates recurring MODEL — which is exactly the discrimination
the doctrine was written to surface.

**No promotion was performed.** Even where the dry-run shows STABLE
eligible, Vision remains EXPERIMENTAL on both routes. Promotion can
only happen through a separate doctrine-aware promotion path
(Roadmap Phase D, not in this commit).

## 12. Open follow-up

- **`uncertainty_honesty` `max_chars` calibration.** The mimo
  SCORER_SUSPECT finding is now reproducible evidence that the
  `max_chars=600` ceiling on `vision-uncertainty-001` is too tight
  for chain-of-thought models. A separate scorer-calibration phase
  should decide whether to raise the ceiling, change the
  anti-rambling metric (e.g. punish after first commitment, not on
  character count), or split the question into a short-answer subform.
  Phase B intentionally does not fix this — it produces the
  evidence and leaves the doctrine evaluator to keep STABLE blocked
  on this route until calibration lands.
- **`vision-object-count-001` on `gpt-5.4-mini`.** The RECURRING_FAIL
  here is a real MODEL miscount — no action required, but worth
  noting in the Vision capability summary when Phase J builds the
  capability-badge UI.
- **Roadmap Phase D (Vision promotion evaluator HTTP read-only).**
  Now unblocked: the doctrine evaluator (Phase A) plus the
  stability evidence written by Phase B is the full input set the
  Phase D endpoint will read.
