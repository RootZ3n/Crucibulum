## 1 · Vision test intent audit summary

Test cards written under `reports/test-validity/cards/vision/`:

| Test | Intent | Concision part of test? | Scorer |
|---|---|:--:|---|
| `vision-ocr-001` | exact OCR | **YES** (the test) | `regex_match` — strict by design |
| `vision-ui-001` | UI clipping diagnosis | NO | `text_match_all` |
| `vision-chart-001` | peak bar identification | YES | `regex_match` |
| `vision-object-count-001` | object recognition + counting | **NO** (recognition only) | `numeric_fact_match` ⟵ NEW |
| `vision-uncertainty-001` | uncertainty honesty | NO | rubric judge (pending) |

The audit found that `vision-object-count-001` was using a scorer
(strict regex + `maxLength: 12`) that punished concision failure
even though the test's stated purpose is recognition + counting.
That's the root cause of the Phase 4 LOW_SCORE.

## 2 · Object-count scoring decision

Kept the test as **recognition + counting**. Recalibrated the
scorer instead of splitting the test (per operator's "Preferred
fix" in the spec). A separate `vision-concise-answer-001` test
will measure concision in a future phase if the operator wants it.

Specific changes to `tasks/vision/vision-object-count-001/manifest.json`:

- Bumped version `1.0.0 → 1.1.0`
- Removed `Reply with ONLY the number` from the prompt (the test
  isn't about concision; the suffix was misleading)
- `scoring_type: regex_match` → `numeric_fact_match`
- Replaced `pattern: ^\s*7\s*$` + `maxLength: 12` with:
  - `expected_number: 7`
  - `expected_number_variants: ["7", "seven"]`
  - `required_object: "red dot"`
  - `max_chars: 600` (chosen because vision models commonly narrate
    their counting reasoning — `mimo-v2-omni` returned ~566 chars on
    Phase 4 with a correct answer at the end)

The bound of 600 chars is generous enough for natural-language
answers but tight enough to catch a true rambler.

## 3 · Scorer changes

`ConversationalScoringType` union extended with `"numeric_fact_match"`.

New optional manifest fields on `ConversationalQuestion`:

- `expected_number?: number`
- `expected_number_variants?: string[]`
- `required_object?: string`
- `max_chars?: number`

New scorer in `core/conversational-judge.ts`:

```
scoreNumericFactMatch(q, response):
  1. Reject if response length > max_chars (default 180; this
     manifest overrides to 600). Reason: "answer too verbose: N chars (max_chars M). Got: …"
  2. Build accepted variants: explicit list OR auto-built {digit, english word for 0–20}.
  3. Search response for ANY variant (digit-style with non-digit boundaries, word-style with word boundaries).
  4. If not found AND another digit IS present → "wrong count: expected X, model said Y".
  5. If not found AND no digit at all → "missing expected count: expected X".
  6. If required_object set AND not substring (case-insensitive) → "missing required object/colour: …".
  7. Otherwise PASS.
```

Each branch reports a specific reason — pinned by tests VS5/VS7/VS8/VS9.

## Remaining Vision risks

- **`vision-uncertainty-001` still needs a real rubric judge.** Until
  it ships, that test stays `--include-uncertainty` opt-in.
- **`vision-ui-001` + `vision-chart-001` haven't had live smoke yet.**
  Defaults to the 2-test smoke set; operator can extend when ready.
- **`max_chars: 600`** chosen for `vision-object-count-001` based on
  one model's behavior. If another vision model is even more verbose,
  may need to widen further or add a `vision-concise-answer-001` test
  that measures concision separately and ranks against it.
- **`required_object: "red dot"` is brittle to phrasing.** A model
  that says "red spots" would fail today. Acceptable for the POC; a
  fuzzy/synonym-aware match could be added later via a custom scorer.
- **Heuristic for `wrong count` detection.** Currently scans for any
  digit ≠ expected; "not 7, but 6 red dots" would PASS on the `7` but
  the spirit is FAIL. Operator-acceptable for MVP; rubric judge fixes
  this nuance.
