# Crucible test-validity audit — 2026-05-25

Final report for the focused audit triggered by the operator's
"425 vs 6" failure question.

## 1. Root cause of the 425-vs-6 failure

The operator's focused-run screenshot showed two **separate**
failures collapsed visually:

- **TE1-Q1** — model answered `6` (expected `16`).
- **TE1-Q4** — model answered `351` (expected `425`).

The screenshot pasted "Got: 6" beside "/^\s*425\s*$/" — but those
strings belong to different questions in the same bundle. Both are
genuine `FAIL_PRODUCT`. Full evidence:
`reports/test-validity/token-efficiency-425-failure.md`.

## 2. Was the test valid?

**Yes.** Independent hand-solve of all 5 token-efficiency-001
questions confirms every expected answer is mathematically correct
under the only defensible interpretation of the prompt:

| Q | Math | Expected |
|---|---|---|
| TE1-Q1 | 18 − 7 + 2 + 5 − 2 | **16** |
| TE1-Q2 | 240 − 85 + 30 − 60 | **125** |
| TE1-Q3 | 92 − 14 + 3 + 21 − 8 | **94** |
| TE1-Q4 | 530 − 142 + 75 − 38 | **425** |
| TE1-Q5 | 47 − 12 + 4 + 9 − 6 | **42** |

Pinned by `tests/scorer-regex-numeric.test.ts` (assertions S1–S7).

## 3. Was the scorer valid?

**Yes.** `regex_match` with pattern `^\s*N\s*$` correctly:

- accepts the canonical answer with leading/trailing whitespace,
- rejects verbose responses (`16 tickets`, `sixteen`, `16.0`,
  etc.) — that strictness is the intentional measurement of the
  token-efficiency family,
- emits an error message naming both the pattern AND what the
  model returned (no silent failure).

Pinned by `tests/scorer-regex-numeric.test.ts` (S2, S7).

## 4. Did the model truly fail?

**Yes — both Q1 and Q4.** `6` is not on any plausible arithmetic
path through Q1; `351` is what the model gets when it sign-flips
the "re-loaned" step in Q4. No retry, provider issue, or hydration
mismatch involved.

## 5. Tests fixed

**0.** No fix needed — the test was already correct.

## 6. Tests quarantined

**0.** No tests required quarantine. The
`docs/TEST_VALIDITY_POLICY.md` document defines the
`manifest.quarantine` block so future tests can be quarantined
honestly without deletion when a real ambiguity surfaces.

## 7. Leaderboard impact

**None.** No tests removed, no rankings re-shuffled. The audit

## What this audit does NOT claim

- It does not certify every Crucible test as valid. Only the
  specific failures in the recent (last 14 days) bundles were
  inspected; the operator has the infrastructure
  (`scripts/test-validity-audit.mjs`) to run the same check again
  any time, against any model or task subset.
- It does not change scorer/runner behavior. Quarantine is an
  opt-in manifest block — future use only.
- It does not promote or demote any model. The leaderboard remains
  exactly as it was.

## What this audit DOES establish

- A reproducible audit flow (the extractor + classifier).
- A policy document defining valid/invalid/quarantined classes.
- Locked-in scorer correctness for the token-efficiency family.
- Hand-verified math for all 5 token-efficiency-001 questions.
- A worked example (the 425 case) other operators can follow.
